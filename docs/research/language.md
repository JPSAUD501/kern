# Research: language data and on-device language models

Status: research, 2026-11-17. Feeds the open decision "language model approach" in `docs/decisions.md`.

Convention: **[V]** = verified this session against the cited primary source (page, paper or file read directly). **[R]** = reported by a secondary or community source, not checked against the primary. **[I]** = inferred or proposed by this research; not a fact about the world, it needs measuring or legal review. This is not legal advice. The license calls below are an engineering reading and should be checked before 1.0.

## 1. Summary and recommendation

### Model approach

1. **A noisy-channel beam decoder over per-language lexicon tries, with a word n-gram LM per language as the LM that is always on.** This is what Gboard shipped as its base ([Ouyang et al. 2017](https://arxiv.org/abs/1704.03987)) and what AOSP LatinIME does. It is the only approach that comfortably fits an 8 ms p99 budget with seven languages active, and it can learn new words the moment the user types them. Correction, completion and next-word prediction are the same search: a hypothesis can be literal, corrected, a completed prefix, or empty (next word). [V for Gboard, I for Kern]
2. **Multilingual mixing by a per-word language posterior, not one merged model.** Each language keeps its own lexicon and LM. The decoder searches all enabled lexicons in one beam. The LM score is a mixture weighted by P(language | sentence so far), modelled as a hidden language state with a small switch probability (HMM-style). Gboard does "on-the-fly, on-device mixing of … monolingual language models" ([Gboard i18n paper](https://arxiv.org/abs/1912.01218)) and SwiftKey estimates the language from the input continuously ([Microsoft support](https://support.microsoft.com/en-us/swiftkey-keyboard/how-to-use-microsoft-swiftkey-keyboard-with-more-than-one-language)). [V that they mix, I for the exact formulation]
3. **A small neural LM as a second stage, added only when the harness shows a gain.** It rescores the top-K word candidates at word boundaries and produces next-word predictions, in the same way as Gboard's "OTF rescoring" and NWP models. Start with something Gboard-sized: a 1-layer CIFG-LSTM with 2.4M–6.4M parameters ([Xu et al. 2023](https://arxiv.org/abs/2305.18465)), or an equally small transformer. A FUTO-sized model (36M parameters, about 31 MB quantized, a forward pass on every keypress) is a later experiment, gated on p99 latency on the reference device. [V for the sizes, I for the plan]
4. **Personalization layered on top, without retraining:** a user lexicon, a decaying user n-gram LM interpolated with the static one, (typed → corrected) undo penalties, and per-key Gaussian touch targets. [I, with Gboard and Fowler et al. as evidence that it pays: WER 5.7% → 4.6% from personalization ([Fowler et al. 2015](https://research.google/pubs/effects-of-language-modeling-and-its-personalization-on-touchscreen-typing-performance/))]

### Data

- **Tier A, ship by default:** Wikipedia including talk pages and Wiktionary (CC BY-SA 4.0), Tatoeba (CC BY 2.0 FR), Common Voice sentence text (CC0), AOSP LatinIME word lists (Apache-2.0, 2014), Leipzig downloads (CC BY), permissive Hunspell dictionaries, Europarl, Common Corpus filtered by per-document license, and **synthetic chat generated by Apache-2.0 open-weight LLMs**. The last one is the main source of conversational register. Google showed that LLM-synthesized chat improves Gboard's next-word accuracy by 19–23% relative over C4 pretraining ([Wu et al. 2024](https://arxiv.org/abs/2404.04360)). [V]
- **Tier B, a decision for João:** web-crawl derivatives (FineWeb-2, HPLT, CulturaX, mC4, OSCAR). The packaging is permissively licensed, but the text belongs to third parties and the Common Crawl ToU applies. Proposal: use them for frequency counts under a high count cutoff, and for neural pretraining only if the harness shows a clear gain. [I]
- **Excluded:** OpenSubtitles (no clear license, listed as CC-BY-NC in one catalogue), Reddit (the Data API terms forbid ML training), Twitter/X, and Stack Exchange (the dump terms conflict with its own license).
- **License consequence:** language packs built from CC BY-SA sources must be distributed under **CC BY-SA 4.0** (or GPLv3, which is one-way compatible), as files separate from the code. This works whichever code license is chosen. Do not feed GPL-only dictionaries (German, Italian, likely pt_PT) into shipped packs. Use them only to measure coverage. [I, based on V license texts]

### Main risks

The legal status of web-crawl-derived statistics and weights. Share-alike propagation into language packs. Scarce, mixed-variant PT-PT data. Synthetic text drifting from how people really write. No real-user typing data, by design. Neural latency on mid-range phones not yet measured. Details in §8.

### 2.2 Why synthetic chat is the backbone of conversational register

- Gboard's own published recipe: prompt an LLM (PaLM 2-S) to (1) filter C4, (2) convert C4 into chat style, and (3) generate chat from persona prompts such as "Imagine you are a [GENDER] at age [AGE]. You are using the [CHAT-APP] APP to message [RECEIVER]…". Pretraining on that data gave **+19.0% and +22.8% relative next-word accuracy on real Gboard user data**, and won in production A/B tests ([Wu et al. 2024](https://arxiv.org/abs/2404.04360)) [V].
- Caveat from the same paper: directly generated chat covered only **79.3%** of the 30K on-device vocabulary, against 99%+ for converted or filtered C4 ([Wu et al. 2024](https://arxiv.org/abs/2404.04360), Table 2) [V]. Synthetic chat must therefore be **mixed with real text** (Wikipedia, Tatoeba, Common Voice, Leipzig) and, if approved, Tier B.
- Gboard's i18n team found that about **10,000 sentences** is enough for a small LM good enough for basic autocorrect and spellcheck in a new language, using elicited free-writing prompts ([Gboard i18n](https://arxiv.org/abs/1912.01218)) [V]. This supports a **volunteer-written, CC0 Kern chat corpus** per language, used mainly as a held-out test set and partly for training. [I]
- Practical (inferred): the RTX 3070 (8 GB) can run a 7–9B model quantized to 4 bits. Generating on the order of 10–50M words per language is feasible over days. Prompts must ask explicitly for each variant (PT-BR vs PT-PT), for informal spellings ("vc", "tbm", "pq", "mdr", "xD", "ahah"), for missing accents at a realistic rate, and for code-switching between enabled languages. [I]

### 3.2 Diacritic restoration ("nao" → "não", "voce" → "você")

- **Evidence from AOSP:** LatinIME's decoder has explicit error types `MATCH_WITH_MISSING_ACCENT`, `MATCH_WITH_WRONG_ACCENT` and `MATCH_WITH_MISSING_EXPLICIT_ACCENT`. A missing accent is in `ERRORS_TREATED_AS_AN_EXACT_MATCH`, with only `ACCENT_ERROR_PENALTY_FOR_EXACT_MATCH = 0.02`. For comparison, `PROXIMITY_COST = 0.0694` and `OMISSION_COST_SAME_CHAR = 0.345` ([error_type_utils.cpp](https://android.googlesource.com/platform/packages/inputmethods/LatinIME/+/refs/heads/main/native/jni/src/suggest/core/dictionary/error_type_utils.cpp), [scoring_params.cpp](https://android.googlesource.com/platform/packages/inputmethods/LatinIME/+/refs/heads/main/native/jni/src/suggest/policyimpl/typing/scoring_params.cpp)) [V]. The pt_BR list also has a few "whitelist" shortcuts (`musica` → `música`, `cafe` → `café`, `atras` (not_a_word) → `atrás`) [V].
- **Kern design** [I]:
  - In the channel model, an unaccented key matches its accented variants (per language: ã/á/â/à for pt; ñ for es; é/è/ê/ë/ç for fr; ä/ö/ü/ß for de; à/è/é/ì/ò/ù for it) at near-zero cost. When the unaccented form is **not a word** in any enabled language ("nao", "voce", "tambem"), the accented word wins and autocorrect applies.
  - When **both forms are valid words** (pt e/é, esta/está, pais/país, sabia/sábia; es si/sí, tu/tú, el/él, mas/más; fr a/à, ou/où; it e/è), the LM context decides. Autocorrect fires only above a confidence margin; otherwise the accented form is offered as a suggestion. This is exactly where the false-correction metric (§6) must gate.
  - Across languages, "e" is valid in pt and it, and "é" in pt and fr. The language posterior must take part in the decision.
  - German: accept "ae/oe/ue/ss" as typed variants of "ä/ö/ü/ß" only as suggestions, because "ss" is standard in de-CH.

### 3.3 Informal spellings and abbreviations ("vc", "tbm", "pq", "blz", "kkk", "mdr", "tqm", "cmq")

- They are **real vocabulary** in chat. AOSP pt_BR already contains `tbm` (flagged `abbreviation`) and `pq` as normal words [V], and Wiktionary documents "vc" [V].
- **Kern design** [I]:
  - Include them in the lexicon with conversational frequencies (from synthetic chat explicitly prompted for them, wordfreq priors and Wiktionary labels).
  - Never autocorrect them to their expansion by default, and never "correct" an expansion into the abbreviation.
  - Offer the expansion as a suggestion only when the app is formal (email field input types) or the user opts in.
  - Learn from undo: if the user reverts "vc" → "você" once, that pair is suppressed (§5).
  - Laughter tokens ("kkkk", "hahaha", "jajaja", "ahah", "mdr") need a pattern rule, not lexicon entries, because their length varies.

## 4. Question 3: model approach on a phone

### 4.1 What the big keyboards actually use

| Keyboard | Published approach | Status |
|---|---|---|
| **Gboard (decoder)** | FST decoder, C∘L∘G composed on the fly. Spatial model: "typically a Gaussian distribution centered on each key center" for taps; a minimum-jerk model or RNN for gestures. Lexicon with optional apostrophes and optional repeated letters. Supports post-corrections. "Keyboard language models should not exceed 5 to 10 Mb … a couple hundred thousand words at most". "A key press is expected to produce visible feedback within about 20 msec". WER: tapping 6.31% → 5.07% with FST plus post-correction ([Ouyang et al. 2017](https://arxiv.org/abs/1704.03987)) | [V] |
| **Gboard (LM, 2018)** | English static LM: "Katz smoothed Bayesian interpolated 5-gram LM containing 1.25 million n-grams, including 164,000 unigrams". "Personalized user history, contacts, and email n-gram models augment the primary LM". The NWP neural model is a single-layer CIFG with 670 units, embedding 96, vocab 10,000, tied embeddings, 1.4M params, and "1.4 megabytes in size" after quantization, on TF Lite. Top-1 recall: n-gram 13.0% vs CIFG 16.4–16.5% ([Hard et al. 2018](https://arxiv.org/abs/1811.03604)) | [V] |
| **Gboard (LM, 2023)** | Same CIFG architecture. NWP vocab 10–20K, OTF (rescoring) vocab about 30K; 2.4M/4.4M/6.4M params for 10K/20K/30K vocab. Pretrained on mC4, fine-tuned with federated learning and DP. More than 20 production LMs, including de-DE, fr-FR, it-IT, es-ES, en-US and pt-BR ([Xu et al. 2023](https://arxiv.org/abs/2305.18465)). The 2024 synthetic-data paper still uses "a one-layer LSTM with 670 hidden units … 30K-size word-level vocabulary … about 6M parameters" ([Wu et al. 2024](https://arxiv.org/abs/2404.04360)) | [V] |

### 4.2 Realistic sizes per language for Kern [I unless marked]

| Component | Size per language | Basis |
|---|---|---|
| Lexicon trie (150–250k forms, frequencies, flags) | 1–3 MB | AOSP pt_BR has 170k words [V]; compact trie or FST [I] |
| Word n-gram LM (3–4-gram, about 1–2M n-grams, quantized trie) | 5–10 MB | Gboard: 1.25M n-grams [V]; "5 to 10 Mb" budget [V]; KenLM-style trie with 1–25-bit quantized probabilities and backoffs, plus lossless pointer compression ([KenLM structures](https://kheafield.com/code/kenlm/structures/)) [V] |
| Neural reranker / NWP (phase 2) | 2–6 MB (int8 CIFG-LSTM, 2.4–6.4M params) | Gboard [V] |
| FUTO-class transformer (experiment) | about 25–40 MB (Q4–Q8 of 36M) | Community port [R] |

With 7 packs enabled that is about 60–100 MB on disk, **memory-mapped** so resident memory holds only the touched pages. Shared neural weights for all languages would be a single multilingual model of about 10–40M params with a shared SentencePiece vocabulary. Per-language models are simpler to evaluate and to ship as optional downloads. **Proposal:** per-language n-grams; neural decided by harness results. [I]

### 4.3 Latency reasoning (8 ms p99 budget) [I, must be measured]

- N-gram lookups cost a few random memory reads per query. A beam of a few hundred hypotheses × 7 languages × (spatial + LM) stays well under 1–2 ms on one big core if lexicon traversal is shared and LM scores are cached per (language, context, word).
- A 36M transformer costs about 72M multiply-adds per token. With a KV cache, each keystroke appends a few tokens, plausibly a few ms on a big ARM core with int8 kernels. Scoring K candidate words needs K × (subword tokens) more forward steps unless they are batched. That is why it belongs **off the critical path** (asynchronous rescoring of the top K that updates the strip), or limited to word boundaries.

### 4.4 Tokenization [I]

- **Decoder and lexicon: words.** Corrections and completions must produce words the user can see, and user-dictionary words must work instantly.
- **Neural model: subword** (SentencePiece unigram, as FUTO does with 15k [R]). It handles open vocabulary (German compounds, Romance clitics such as "dá-me", "dímelo") and lets a word score be a sum of subword log-probabilities. Gboard's word-level 10–30K vocab [V] is simpler but leaves the long tail to the n-gram.
- **Character-level** (as in FUTO's `<CHAR_*>` tokens [R], or Adhikary's 12-gram character LM [V]) lets the model correct directly. Keep it as a research option; it moves the spatial model inside the network, which hurts explainability and the undo guarantees.

### 4.5 Combining languages (code-switching) [I; mixing itself V for Gboard]

- Hidden language state per word ℓᵢ ∈ enabled languages, with P(ℓᵢ | ℓᵢ₋₁) = 1 − s if equal and s/(n−1) otherwise. Tune s on code-switched synthetic test data (start around 0.05–0.15).
- Candidate score = spatial log-likelihood + log Σ_ℓ P(ℓ | history) · P_ℓ(w | context_ℓ). Words shared across languages ("no", "a", "de", "come") naturally get mass from several LMs.
- Each language LM keeps its own context. After a switch it backs off to shorter context, never to a cross-language n-gram.
- The prior comes from the user's enabled languages, usage counts and `EditorInfo.hintLocales` ("List of the languages that the user is supposed to switch to no matter what input method subtype is currently used", [Android docs](https://developer.android.com/reference/android/view/inputmethod/EditorInfo)) [V].
- **PT-BR and PT-PT** are two languages that share most of the lexicon but have separate frequencies and LMs (você/tu, ônibus/autocarro, fato/facto). Enabling both should not double-count shared words.

## 5. Question 4: correction and decoding

**Shared decoder (proposed, following Ouyang et al. [V]):**

1. **Input:** a sequence of touch points (x, y, time). The spatial model gives log P(touch | key) as a 2D Gaussian per key. Its means and covariances start from the layout and adapt per user (Bayesian update from committed words, aligned to their taps).
2. **Search:** token-passing beam search over the union of lexicon tries. Edit operations are proximity substitution, omission, insertion, transposition, accent variants, case, optional apostrophe and repeated letters (all in Gboard's L transducer or in LatinIME's error types [V]), plus a space-omission or merge path for "missing space".
3. **Score:** spatial + edit penalties + λ·LM mixture (§4.5). Literal typing is always a hypothesis, so the user can type out-of-vocabulary words.
4. **Outputs from the same beam:** (a) literal, (b) best correction, (c) completions = best prefix hypotheses extended with the most likely words below that trie node (precomputed max-frequency per node), and (d) next-word prediction = the zero-input state after a commit.
5. **Autocorrect decision:** apply only if score(best) − score(literal) exceeds a per-language threshold tuned on the false-correction rate, and never when the literal is a user-dictionary word.
6. **Post-correction** (Gboard: the following word fixes "a while lot" → "a whole lot" [V]): allowed only on the immediately previous word and shown visibly. Phase 2.

**Personalization without retraining** [I; layered n-grams V for Gboard]:

- **User lexicon:** words typed literally and kept (not reverted) N times are added. The user can add or remove words. Shortcuts ("vc" → "você" only if the user wants it).
- **User n-gram:** bigram/trigram counts with exponential decay, interpolated with the static LM (Gboard: "Personalized user history, contacts, and email n-gram models augment the primary LM" [V]). Fowler et al.: personalization brought WER from 5.7% to 4.6% [V]. Adhikary et al.: +9.9% relative keystroke savings from personalization ([Adhikary et al. 2023](https://www.keithv.com/pub/personalization/adhikary23_interspeech.pdf)) [V].
- **Learning from undo:** when a backspace right after an autocorrect restores the literal, record (literal, correction, context-hash). Add a decaying penalty that blocks that correction, and add the literal to the user lexicon after repeated reverts. This is cheap, explainable and inspectable.
- **Touch model:** online per-key Gaussian updates, bounded so they don't drift.
- **Neural personalization** (FUTO-style LoRA [R]) is optional and later. Never learn in fields flagged `IME_FLAG_NO_PERSONALIZED_LEARNING` or password fields (a product non-goal).

## 6. Question 5: evaluation

**Metrics** (all per language and per mixed-language set):

| Metric | Definition | Source |
|---|---|---|
| WER after decoding | Word error rate of the final text against the reference, with simulated sloppy taps and no backspace | Fowler 2015, Adhikary 2023 [V] |
| Keystroke savings (KS) | "Percentage reduction in keys pressed compared to letter-by-letter" entry; selecting a prediction counts as 1 keystroke | Adhikary 2023 [V] |
| Prediction top-1/top-3 recall | Fraction of words whose next-word prediction matched, for the center slot and the 3-slot strip | Hard 2018 [V] |
| **False correction rate** | Fraction of correctly typed words (literal = reference) that autocorrect changed. Kern's main "never in the way" metric. Report it separately for accent pairs and informal words | Proposed [I]; Ouyang 2017 notes such corrections are "very frustrating" [V] |
| Missed correction rate | Fraction of erroneous literals left uncorrected while the reference was in the top-1 | Proposed [I] |
| Language-ID accuracy per word on code-switched text | — | Proposed [I] |
| Latency p50/p99 per keystroke, memory | Run in the harness on the reference device | product.md |

The trade-off between completion and correction is a known Pareto frontier ([Bi, Ouyang, Zhai, CHI 2014, "Both complete and correct?"](https://www.researchgate.net/publication/266655701_Both_complete_and_correct_Multi-objective_optimization_of_touchscreen_keyboard)) [R]. Report both, not a single score.

**Simulating realistic noise:**

- **Spatial:** tap the key center plus Gaussian noise, SD **2.0 mm in x, 1.9 mm in y**, as used by Adhikary et al. following Fowler et al. and Azenkot & Zhai ([Adhikary 2023](https://www.keithv.com/pub/personalization/adhikary23_interspeech.pdf)) [V]. Also sweep the SD to simulate sloppy and careful users. [I]
- **Cognitive and orthographic noise** [I]: omissions, transpositions and doubled letters (rates mined from natural typos), dropped accents (per-user rates from 0% to 100%, since many people never type accents), dropped apostrophes, missing spaces, informal abbreviations kept as is (they are not errors), and language switches.
- **Remulation:** replay recorded real touch traces through the decoder ([Octopus, Bi et al. CHI 2013](https://research.google/pubs/octopus-evaluating-touchscreen-keyboard-correction-and-recognition-algorithms-via-remulation/)) [V]. Kern should collect an **opt-in, consented, CC0 touch-trace and chat-text dataset** from volunteers, through an in-app study mode that is off by default and exports a file the user sends themselves. That respects "no project server". [I]

**Test corpora** [I unless marked]:

- Held-out conversational text per language: the Kern volunteer chat set (primary), Tatoeba held-out split, Common Voice sentences, UD social/spoken treebanks (EN-EWT, IT-TWITTIRO, FR-ParisStories/Rhapsodie; CC BY-SA [V]), Common Voice Spontaneous Speech transcripts (CC0 [R]), and a synthetic chat held-out set from a **different** generator than training.
- Natural misspellings: mine Wikipedia revision diffs (CC BY-SA) for one-word edits within a small edit distance. The GitHub Typo Corpus has 350k edits in 15+ languages, mostly English, with per-repo licenses, so it is internal eval only ([repo](https://github.com/mhagiwara/github-typo-corpus)) [V].
- Diacritics: the 12-language Wikipedia-based corpus from Náplava et al. ([LREC 2018](https://aclanthology.org/L18-1247/), [LINDAT](http://hdl.handle.net/11234/1-2607)) [R]; license not verified, check before use.
- Real typing behaviour: the 37K mobile typing dataset ([Palin et al. 2019](https://userinterfaces.aalto.fi/typing37k/)) logs keystrokes from 37,370 participants. **No license stated** [V]; contact the authors before relying on it.

## 8. Open risks

1. **Legal status of web-crawl derivatives (Tier B).** FineWeb-2, HPLT and mC4 license only the packaging. The text belongs to third parties, and the CC ToU disclaims rights and requires indemnity, including for AI training [V]. Distributing pruned n-gram counts is lower risk than weights, which are lower risk than text [I]. **Decision needed from João:** ship Tier A only, or accept Tier B for counts and weights.
2. **Share-alike propagation.** Packs built from Wikipedia, Wiktionary or wordfreq must be CC BY-SA 4.0 (or GPLv3 via one-way compatibility [V, [CC compatible licenses](https://creativecommons.org/share-your-work/licensing-considerations/compatible-licenses/)]). Keep packs as separate artifacts with their own LICENSE and an in-app credits screen. GPL-only dictionaries (de, it, probably pt_PT) cannot go into CC BY-SA packs; GPL + BY-SA can only combine as GPLv3. Using them for evaluation only avoids the issue. [I]
3. **Attribution bookkeeping.** Tatoeba needs per-author credit, Leipzig an attribution line, ODC-By an attribution, YouTube-Commons channel credit. The pipeline must generate `ATTRIBUTION` files reproducibly (D6). [I]
4. **PT-PT scarcity and variant contamination.** Most Portuguese data is unlabelled or Brazilian-dominated. Without care, PT-PT users get PT-BR suggestions (você, ônibus, "fato" for "facto"). [I]
5. **Synthetic data distribution gap.** LLM chat is cleaner, more polite and less diverse than real chat. Google measured only 79.3% vocabulary coverage [V]. It needs mixing, diversity prompts, and evaluation on human-written held-out text, not on synthetic text from the same generator. [I]
6. **No real user data, by design** (no telemetry, no federated learning). Gboard's gains come partly from FL on real typing [V]. Kern must make up for it with volunteer-contributed CC0 sets and on-device personalization. [I]
7. **Neural latency and battery** on the (not yet chosen) mid-range reference device are unmeasured. FUTO's per-keystroke forward pass is reported to cost battery [R]. Neural stays phase 2, behind the harness. [I]
8. **Leipzig license version ambiguity** (CC BY vs BY-NC across catalogues) [R]. Pt_PT Hunspell license wording is ambiguous [V]. Verify both before use.
9. **Generator licenses drift.** Re-check the license of any LLM used for synthesis at generation time, pin the exact model revision and its license text in the data manifest, and avoid licenses that claim models trained on outputs. [I]
10. **Offensive vocabulary.** Do not suggest it unless the user typed it. AOSP `possibly_offensive` flags are a permissive starting point [V]; they are 2014-era and English-centric in quality [I].
